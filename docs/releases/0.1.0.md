# Contextbook 0.1.0 Release Notes

Contextbook v0.1.0 is the first MVP release.

It is a local CLI for one job:

> Learn the concepts behind the code you just touched.

Instead of asking an AI to explain a random file, you scan your project and ask Contextbook what concepts are visible in your own code.

## Who should try this

Try Contextbook if you have said something like:

- “I used SSE or WebSocket, but I cannot explain the concept clearly.”
- “I know this React pattern works, but I want better interview language for it.”
- “Generic CS study feels disconnected from my project.”
- “I want AI coding sessions to remember how I prefer explanations.”

The first target users are project-based frontend developers, interview-prep developers, and developers using tools like Codex/OMX or Claude Code.

## Install

```bash
npm install -g contextbook
contextbook setup
contextbook doctor
```

`contextbook setup` installs local helper files for Codex/OMX and Claude Code. It creates helper scripts and guide files, but it does not silently overwrite existing hook config.

Useful checks after setup:

```bash
contextbook hooks status
contextbook hooks smoke --prompt "why does cleanup matter?" --json
```

## First project flow

Inside a project:

```bash
contextbook init
contextbook scan
contextbook learn
contextbook why "why does cleanup matter?"
```

What each command does:

| Command | Meaning |
| --- | --- |
| `contextbook init` | create local project memory and default learner files |
| `contextbook scan` | find deterministic code signals such as imports, hooks, files, diffs, and concept keywords |
| `contextbook learn` | recommend 1-3 learning moments from the project |
| `contextbook why "..."` | answer a concept question with project evidence when available |

After setup, agent shortcuts are also available where supported:

| Environment | Learning moments | Concept question |
| --- | --- | --- |
| Codex/OMX | `$learn` | `$why "why does cleanup matter?"` |
| Claude Code | `/learn` | `/why "why does cleanup matter?"` |

## The three memories

### Project Memory

Project Memory is stored in the project under `.contextbook/`.

It stores project facts: dependencies, changed files, imports, file/function names, detected concepts, evidence files, scan runs, and file index snapshots.

### Learner Memory

Learner Memory is stored outside the project under `~/.contextbook/learners/default/`.

It stores learning preferences, weak terms, answer history, profile update audit events, and safe learning signals.

This is outside the repo so personal learning data is not committed with project code.

### Conversation Memory

Conversation Memory is append-only structured event history.

It records small events such as scan, learn, why, profile, and explicit prompt-signal capture. It is not a raw chat transcript.

## What answers look like

Contextbook always reports an evidence level:

| Evidence | Meaning |
| --- | --- |
| `direct` | direct project evidence exists |
| `related` | nearby or structural project evidence exists |
| `general` | no project evidence found; answer should be uncertainty-first |

`contextbook why` can render in different shapes depending on the question and memory:

- narrative explanation
- plain-language explanation
- structured summary
- interview answer
- uncertainty-first answer for general evidence

The point is not to produce a fixed template. The point is to explain the concept in a way that fits the project evidence and the learner’s current preference signals.

## Safety boundaries

v0.1 is deterministic-first and local-first:

- no external LLM/API key required
- no cloud sync
- no raw prompt persistence by default
- no silent learner judgment
- no automatic weak-term/profile promotion from ambiguous chat
- low-risk preference automation only through backup/audit/undo
- restore, repair, recover, profile, and weak-term updates remain explicit

## Not included yet

Not in v0.1:

- web dashboard
- cloud sync
- external LLM calls
- full knowledge tracing model
- team-shared learner memory
- broad language/framework coverage beyond deterministic signal rules
